## [Unreleased]

### Added
- `cassandra-verify-versions` derives the expected JDK and the AxonOps java agent jar from the Cassandra version being tested instead of hardcoding 5.0's. It asserted `version "17` with the message "expected Java 17 for Cassandra 5.0" and looked for `axon-cassandra5.0-agent.jar`, so a correct 4.x image failed the check on the JDK 11 base image it is supposed to run on — confirmed against 4.0.21 and 4.1.12, both of which started Cassandra and the agent cleanly and failed only this assertion. `k8ssandra-verify-versions` already branched on the major version; this brings the standalone image's action in step.
- Cassandra **4.0** and **4.1** are published lines. Both were `published: false` in `versions.yaml` on the grounds that the AxonOps agent was not compatible with their JDK 11 base images; the `axon-cassandra4.0-agent` and `axon-cassandra4.1-agent` RPMs are in the AxonOps yum repository and `k8ssandra/4.1/` had already been brought in step with 5.0, so the blocker is recorded rather than real. `build_matrix` now lists 20 versions for 4.0 (4.0.0 – 4.0.21; 4.0.2 and 4.0.16 have no `cass-management-api` base image and are skipped) and 13 for 4.1 (4.1.0 – 4.1.12), taking both published images from 9 build jobs to 42. `k8ssandra/4.0/` was two releases behind and would have built the wrong image: its Dockerfile had no `INCLUDE_MGMT_API`, `AXON_AGENT_VERSION` or `AXON_AGENT_JAVA_VERSION` arguments, so the standalone `ghcr.io/axonops/cassandra/cassandra` build would have shipped the Management API it is defined by not having, and the agent version inputs would have been silently ignored; it also pulled its base from `docker.io` rather than `ghcr.io` and set the java agent through `JVM_EXTRA_OPTS` instead of writing `axonops-jvm.options`. It is now generated from the 4.1 Dockerfile, and its entrypoint — 285 lines behind, missing the `AXON_AGENT_NTP_HOST` default and the `cassandra-env.sh` idempotent append among others — is replaced with the shared one, which is byte-identical across all three lines.
- `build_matrix.lines` is ordered oldest line first, and the field reference says why: `build-matrix.sh newest` takes the last version of the last published line, so with 5.0 listed above 4.1 and 4.0 the newest version would have been reported as 4.0.21. That decides the version the publish workflows build for their pre-publish test and the version the e2e and cloud-install tests default to. The floating tags themselves were never at risk — `k8ssandra-determine-latest` sorts with `sort -V` — so `latest` continues to resolve to 5.0.9 and each line gets its own `{line}-latest`.
- The Cassandra release notes list one `{line}-latest` tag per published line instead of hardcoding `5.0-latest`, which named a single line while the workflow published three.
- Cassandra **5.0.9** enters the build matrix, and the k8ssandra Management API moves from 0.1.124 to **0.1.125** ([#194](https://github.com/axonops/axonops-containers/issues/194)). 5.0.9 has been released by Apache since June but could not be built here: these images are built `FROM ghcr.io/k8ssandra/cass-management-api`, and no 5.0.9 base image existed. k8ssandra published one at v0.1.125, so the blocker recorded in `versions.yaml`, `k8ssandra/README.md` and `UPDATING_K8SSANDRA_VERSIONS.md` is gone and every one of those notes is removed rather than left to rot. 5.0.9 is now the newest supported version, so `latest` and `5.0-latest` resolve to it once the next build publishes. The `K8SSANDRA_VERSIONS` repository variable is rewritten with the v0.1.125 digests for all 39 previously listed versions plus 5.0.9, and picks up 4.0.21 and 4.1.12 so the unpublished 4.x lines stay complete and do not need a second pass when the AxonOps agent JDK 11 blocker is lifted. `scripts/build-matrix.sh check` passes against the new variable. Note that the last published image, `5.0.8-v0.1.120-1.5.6`, was built against v0.1.120 — the variable had already moved to 0.1.124 without a rebuild — so the next build crosses two API versions, not one. The published version lists in the root `README.md`, `k8ssandra/README.md` and `cassandra/README.md` are updated with their French translations, the `k8ssandra-e2e-test` input example no longer names a tag that was never published, and `UPDATING_K8SSANDRA_VERSIONS.md` gains a history row.
- The K8ssandra image entrypoints default `AXON_AGENT_NTP_HOST` to `pool.ntp.org` and warn on every start until it is overridden ([#190](https://github.com/axonops/axonops-containers/issues/190)). The agent auto-detects the host's NTP configuration, but that cannot work in a container with no `ntp.conf` or `chrony.conf` to read, so it fell back to a public NTP pool of its own choosing, invisibly. Clock-skew readings were therefore taken against a public pool the Cassandra nodes never sync with, and nothing in the logs said so. The default is now set explicitly in the entrypoint, next to the existing `AXON_AGENT_SERVER_HOST` and `AXON_AGENT_SERVER_PORT` defaults, and three warning lines name the variable and show the `host:port` form. A supplied value is also checked: a non-numeric or out-of-range port is reported as a warning rather than a failure, because a wrong NTP host is not a reason to stop a Cassandra node from starting. Behaviour is unchanged for anyone who already sets the variable — CI already passes `AXON_AGENT_NTP_HOST=time.google.com`. `k8ssandra/README.md` documents the variable, its default and the warning; the French translation follows.
- `docker-compose/04-cassandra-cluster-and-config/` — the AxonOps platform and one monitored Cassandra node, with the cluster's alerting defined in `config.yaml` and applied by a one-shot `ghcr.io/axonops/axonops-ansible-ee` container that runs the `axonops.axonops.configurations` role against the API and exits. The other examples leave a reader to click alert rules into the dashboard by hand, which is neither reviewable nor repeatable across clusters; this one puts the rules in a file next to the Compose stack, and `docker compose run --rm config` re-applies it idempotently after an edit. Two metric alert rules are active; log alert rules, TCP and shell service checks, a Slack integration and an alert route ship commented out with the fields each takes. The README documents every metric-alert-rule field, the role's tags for applying part of the configuration, the Slack webhook coming from `.env` rather than the playbook, and the two failure modes that are silent rather than loud — a `dashboard`/`chart` name that does not match the UI is accepted and simply never evaluates, and the modules censor their own output by default, which hides API errors until `enable_logging: true` turns it back on. `README.fr.md` translated in step, and both files join the `Docs Translations` in-scope list and the llms.txt index.
- The Cassandra build matrix is declared once, in a new `build_matrix` section of `versions.yaml`, and read by every workflow through `scripts/build-matrix.sh` ([#158](https://github.com/axonops/axonops-containers/issues/158)). Nine workflow files each carried their own copy of the version list and they had already drifted three ways: the production publish matrix built 5.0.1 and 5.0.2 while its own `ALL_VERSIONS` started at 5.0.3, so those two versions were published but never checked for an existing tag; `k8ssandra-build-and-test` still tested up to 5.0.7 after everything else moved to 5.0.8; and the cloud install test pinned 5.0.7 against a development image that had never been published for it. Matrices, `ALL_VERSIONS`, the newest-version defaults, the floating `latest` and `{line}-latest` tag conditions, the nightly CVE scan list and the generated release notes are now all derived from the one list — the notes previously hardcoded the version set, the tag count and the Management API version, and stated a set that no longer matched the build. One list covers both Cassandra images, because they are built from the same `k8ssandra/<line>/Dockerfile` and the same base digest and can never legitimately differ.
- `scripts/build-matrix.sh check` runs before anything is built in the publish, build-and-test and cloud-install workflows. It fails when a version has no `cass-management-api` base image in `K8SSANDRA_VERSIONS`, when a published line lists no versions, when an unpublished line gives no reason, when a version is listed under the wrong line, or when a published line has no build directory. The 5.0.9 mistake — a version in the matrix that k8ssandra publishes no base image for — is exactly what the first of those catches, in seconds rather than 15 minutes into a build.
- The supported-version policy is stated in the root `README.md` and `k8ssandra/README.md`: when a version is added (Apache has released it *and* k8ssandra has published the base image), that versions are kept and rebuilt rather than retired when a newer patch appears, that a line is dropped only at upstream end-of-life, and that 4.0 and 4.1 are retained-but-unpublished with the AxonOps agent JDK 11 incompatibility as the recorded reason. Both files' French translations updated in step.
- `k8ssandra-e2e-test` defaults its `cassandra_version` input to the newest published version instead of a hardcoded `5.0.8`, and `cassandra-build-and-test` triggers on `k8ssandra/**` rather than only `k8ssandra/5.0/**`, so a change to a line other than 5.0 no longer skips the standalone image's tests.
- `k8ssandra-cloud-install-test` checks the development image exists before creating the cluster, and dumps pod status, describe output, recent events and cass-operator logs when the cluster fails to become ready. The run that prompted this reported only `error: timed out waiting for the condition on pods/axonops-dev-cass-dc1-default-sts-0` after 15 minutes; the actual cause was a missing `5.0.8` development image, which the new check reports immediately. The check writes the tag list to a file before searching it: piping `gh api` straight into `grep -q` kills `gh` with `SIGPIPE` as soon as the tag matches, and `pipefail` then turned every present image into a reported-missing one. It also declares `packages: read` and treats an API error as "cannot tell" rather than "image missing", so a token without package access no longer fails the job before the cluster is created.

- The Cassandra container healthcheck now also verifies the AxonOps agent, so a node whose `axon-agent` has died is no longer reported as healthy while silently missing from AxonOps ([#168](https://github.com/axonops/axonops-containers/issues/168)). A dead agent is reported in the healthcheck output but does not fail the check by default — Cassandra is still serving CQL, and failing it can make an orchestrator restart or drain a working node. `HEALTHCHECK_REQUIRE_AGENT=true` opts in to treating it as a failure. The agent is found by walking `/proc`, so nothing new is installed in the image.

Found by sweeping for the same pattern as the `cassandra-env.sh` append below; `plugins.security.ssl.http` already deleted before appending and was left alone. Applies to both 3.3.2 and 3.7.0.
- `axondb-search` deletes `plugins.security.ssl.http` with the entrypoint's own `_sed-in-place` helper instead of `sed -i`. `sed -i` replaces the file by renaming a temporary over it, which fails when the file is bind-mounted — the reason the helper exists. Both other edits in these entrypoints already used it.
- The Cassandra image entrypoint appends `. /usr/share/axonops/axonops-jvm.options` to `cassandra-env.sh` only when it is not already there. The append was unconditional, which is harmless while the file is part of the image layer but not when it is bind-mounted or on a volume: the line then survives the container and another identical one is added on every restart, growing without bound. Confirmed against the published image — one restart takes it from one line to two.
- `axondb-search-publish-signed` passes the OpenSearch version it is building to its two verification steps. It took out the first 3.3.2 build at 1.6.1. The development and build-and-test workflows already passed these correctly.
- The three examples that run `axondb-search` use `3.7.0-1.6.1`, the build carrying the `opensearch.yml` entrypoint fixes — `OPENSEARCH_DISCOVERY_TYPE` is applied at last, and `path.repo` and `plugins.security.disabled` no longer duplicate on a mounted config. They still pass OpenSearch's native `discovery.type=single-node` alongside it, deliberately, so the files keep working against earlier images; the comment above it now says that rather than claiming the fix is unshipped. `versions.yaml` and `VERSIONS.md` record the release.
- All four `docker-compose/` examples use `ghcr.io/axonops/cassandra/cassandra:5.0.8-2.0.31-1.1.0`, the release carrying the `CASSANDRA_AUTHENTICATOR` entrypoint support and the agent-aware healthcheck. ### Fixed
- The `axon-server` chart renders a `containers:` key for every combination of `persistence.enabled` and `persistence.enableInitChown` ([#198](https://github.com/axonops/axonops-containers/issues/198)). The key sat inside the `{{- if and .Values.persistence.enabled .Values.persistence.enableInitChown }}` block that guards the `fsgroup-volume` init container, so with either value `false` it was never emitted and the `axon-server` container was rendered as the last item under `initContainers:` instead. The pod spec then had no `containers:` at all and the API server rejected it with `spec.containers: Required value`, so the release failed to install — no StatefulSet, no pod, and an error naming the pod spec rather than the value that was changed. Both values default to `true`, so a default install was never affected; disabling persistence for an ephemeral or CI install, or disabling only the init chown because the storage class already sets ownership or because the cluster's Pod Security Standards forbid its `runAsUser: 0`, was. `initContainers:` was also emitted unconditionally and is now inside the guard, so it no longer renders as a bare key with no items. This is what the sibling charts already do — `axondb-search` and `axondb-timeseries` both wrap the `initContainers:` key in its own conditional and keep `containers:` outside it. The default render is byte-identical to 2.1.14, so nothing changes for an existing install; the chart version and the umbrella chart's dependency pin go to 2.1.16, skipping the 2.1.15 that the CI appVersion bump already published from `main`.
- The AxonOps agent data volume mounted at `/var/lib/axonops` in the K8ssandra example is no longer hard-coded to `512Mi`, and its default grows to `2Gi` ([#188](https://github.com/axonops/axonops-containers/issues/188)). Every other storage and resource value in `examples/k8ssandra/cluster-axonops-ubi.yaml` was templated from `k8ssandra-config.env` — even the `storageClassName` on this same volume — so the one literal could not be changed the way the example teaches, and `512Mi` is small enough to fill up on a busy node, which stops the agent writing its local data. The size now comes from a new `AXONOPS_STORAGE_SIZE` variable, and the composite action `.github/actions/k8ssandra-deploy-cluster` takes an `axonops_storage_size` input with the same `2Gi` default. The English and French k8ssandra READMEs show the variable and warn that most StorageClasses cannot shrink a volume after creation, so the size has to be chosen before the first apply; existing deployments do not resize on their own and need the PVC expanded or recreated.
- `k8ssandra/README.md` contained two `Supported Cassandra Versions` sections that disagreed: one listed 5.0.1 to 5.0.8, the other 5.0.1 to 5.0.6. The second is now a `Cassandra Lines` table covering what actually differs between the lines — base image, JDK, build directory, published or not — and points at the single list for the versions.
- `k8ssandra/README.md` carried a full base-image digest mapping labelled "k8ssandra API v0.1.120". The live `K8SSANDRA_VERSIONS` variable had moved to v0.1.124, so every digest in the table was wrong, and nothing in CI compared the two. The table is replaced by the command that reads the variable. Same fix in the French translation.
- Cassandra 5.0.9 removed from the K8ssandra production publish workflow ([#158](https://github.com/axonops/axonops-containers/issues/158)). `ALL_VERSIONS` and the `k8ssandra-build-push-sign` matrix both listed 5.0.9, but these images are built `FROM ghcr.io/k8ssandra/cass-management-api` and k8ssandra publishes no 5.0.9 base — there is no `5.0.9+*` key in `K8SSANDRA_VERSIONS` either, so the 5.0.9 job could only fail with "No k8ssandra version found", and having it in `ALL_VERSIONS` also pointed the `5.0-latest` and `latest` floating tags at a version that is never built. The newest supported K8ssandra line is 5.0.8, and `k8ssandra/README.md` and `k8ssandra/UPDATING_K8SSANDRA_VERSIONS.md` now state the rule that a Cassandra version cannot enter the matrix before k8ssandra ships its base image.
- The K8ssandra workflows that still pinned 5.0.7 now use 5.0.8, the newest version with a `cass-management-api` base: the `k8ssandra-build-and-test` default and the version its secondary matrix runs after, the `k8ssandra-development-publish-signed` test matrix, its build matrix (which stopped at 5.0.7) and the `5.0-latest` and `latest` tags it pushes, the `k8ssandra-cloud-install-test` cluster version, and the `k8ssandra-e2e-test` default. The development images' floating tags therefore resolved to 5.0.7 while production resolved to 5.0.8.

- `docker-compose/03-secure-3-rack-cluster/` pinned only `cassandra01` to the image that honours `CASSANDRA_AUTHENTICATOR`; `cassandra02` and `cassandra03` were left on the production tag, which ignores it. Two of the three nodes therefore joined the "secured" cluster with `AllowAllAuthenticator` and accepted unauthenticated connections on their own published CQL ports, while the README stated all three ran the newer image. All three now use it, and the README's verification step checks every node rather than the first.
- The Cassandra nodes in `docker-compose/` examples 01, 02 and 03 replaced the image's healthcheck with their own `nodetool statusbinary` test, which bypassed the agent check added to `axonops-healthcheck.sh` — the exact failure that check exists to catch, a node serving CQL while its `axon-agent` is dead and the node has vanished from AxonOps. They now run the image's own script, and each README documents `HEALTHCHECK_REQUIRE_AGENT`.
- `docker-compose/00-axonops-platform/docker-compose.yaml` carried stale `Preferred (immutable)` digests for `axondb-timeseries` and `axondb-search` — neither matched the version tag beside it, or the digest in `VERSIONS.md` and the other examples. Following the file's own advice to deploy the digest form pulled a different image from the one the tag resolves to. Its section headers also named the previous Cassandra and OpenSearch versions.
- `docker-compose/01-cassandra-cluster/README.md` documented `AXONOPS_CASSANDRA_SSL` as defaulting to `true`. The default is `false`, as the same README's troubleshooting section explains it must be — anyone setting it from the table hit `Invalid or unsupported protocol version (22)` and a backend that would not start.
- `AXONOPS_ORG_NAME` had three different documented defaults across the self-hosted examples: `example` in the Compose files, `my-organization` in `env.example`, and one of each in the READMEs. All now say `example`. Example 02 is unchanged — it has no default, because a SaaS organisation name cannot be guessed.
- The root `README.md` listed three Compose stacks; there are four. Example 03 was missing.
- `docker-compose/03-secure-3-rack-cluster/` referred to "the eight `ipv4_address` entries" in the README and the Compose file. There are seven.
- `cassandra-publish-signed` and `k8ssandra-publish-signed` pushed tagged images *before* running their verification steps, so any post-push failure left published tags that were never verified and never signed. This happened on the Cassandra 1.0.0 run: 5.0.3 was pushed, failed its cqlai test, skipped signing, and sat in the registry unsigned. Both pipelines now push by digest only, run the test suite, sign the digest, and apply tags last with `docker buildx imagetools create` — asserting that every tag resolves to the digest that was signed. A failure at any stage now leaves nothing pullable by tag.
- `k8ssandra-publish-signed` re-ran the entire multi-arch build after signing purely to re-apply tags. That second build is gone; tagging copies the existing index instead.

### Fixed
- `k8ssandra-test-cqlai` verified query output by piping `cqlai` straight into `grep -q`. `grep -q` exits on the first match, SIGPIPEs `cqlai`, and under `pipefail` the step fails with exit 141 whenever the write loses the race — it took out a Cassandra 5.0.3 publish job. The output is now captured before matching.
- `fail-fast` disabled on the `cassandra-publish-signed` and `k8ssandra-publish-signed` build matrices. One version failing was cancelling every other version mid-publish, which can leave a release half-pushed with inconsistent floating tags.
- `docker-compose/01-cassandra-cluster/` connected to `axondb-timeseries` with `CQL_SSL=true` while the Cassandra native transport was plaintext, so `axon-server` never started: Cassandra logged `Invalid or unsupported protocol version (22)` (the first byte of a TLS ClientHello read as a CQL protocol version) and `axon-server` logged `tls: first record does not look like a TLS handshake`. The image only enables `client_encryption_options` when a keystore is mounted at `CASSANDRA_KEYSTORE_PATH` — `CASSANDRA_CLIENT_ENCRYPTION_ENABLED`, which the example passed, does nothing — so `CQL_SSL` now defaults to `false` and the two no-op variables are gone.
- `docker-compose/01-cassandra-cluster/` set `AXON_SERVER_URL` for `axon-dash`, which the dash accepts through its loose `AXON_SERVER_*` prefix mechanism and silently ignores, leaving `private_endpoints` at `http://127.0.0.1:8080` — itself — so it crash-looped with `findHost | no reachable endpoints`. Now uses `AXONSERVER_PRIVATE_ENDPOINTS`, the name its section-and-key mapping actually expects.
- `axondb-search` never applied `OPENSEARCH_DISCOVERY_TYPE`. The entrypoint printed it in the startup banner and the README documented it with a default of `single-node`, but nothing wrote `discovery.type` to `opensearch.yml` and the variable was never defaulted. With `network.host` at `0.0.0.0` OpenSearch runs its production bootstrap checks and refuses to start: `the default discovery settings are unsuitable for production use`. Both the 3.3.2 and 3.7.0 entrypoints now default the variable to `single-node` and write it to `opensearch.yml`.
